# Integration suite for the components of CoOpeRace

A regression check of the archive's components on a few small tasks of each of the four properties of `C.Concurrency` (no-data-race, unreach-call, no-overflow, valid-memsafety), not the hours of a run over the categories. With `-j 15` it takes about 4 minutes on `goblint` (16 cores, BenchExec 3.35); one run at a time, without `-j`, about 15 minutes. For each component of the production configuration `conf/svcomp27.json` (Goblint, Dartagnan, sv-sanitizers, Deagle, ULTIMATE GemCutter) it asks whether the component, run inside CoOpeRace, gives the verdict it gives alone, and whether the witness CoOpeRace delivers is in the format SV-COMP 2027 requires (YAML, `witness.yml`), is accepted by WitnessLint and is confirmed by a validator of SV-COMP 2027: a violation witness for a `false`, and a correctness witness for a `true` of unreach-call and no-overflow. It also runs `conf/svcomp27.json` on every task, including one task per property on which phase 1 of the strategy answers nothing and phase 2 answers (the hand-over, check 8). Each task is run for one property, the `property` of its entry in `manifest.json` (no-data-race where it names none).

```sh
python3 scripts/download-tools.py            # tools/, once; with --pool also ULTIMATE Automizer and iekke
python3 scripts/download-validators.py       # validators/, once
python3 tests/integration/run.py -j 15       # or: make integration (one run at a time)
```

`-j CORES` lets the suite use CORES cores at a time, that is CORES // `--cores` runs at a time (7 with `-j 15` and 2 cores per run). The suite does not name cores: it takes the first CORES of the cores its process may use (or of `--allowed-cores`), and each stage (verification, validation, linting) runs its `benchexec` calls in lanes at the same time, each lane on its own cores with a share of the runs at a time by its number of runs, the calls of a lane one after the other; BenchExec places each run on its lane's cores. Without `-j`, the calls run one after the other, each with `-N` runs at a time (default 1).

The SV-COMP 2027 versions of some validators are proposed in fm-tools merge requests that are open on 2026-10-17 (ULTIMATE Automizer !1172, Theta !1196, ConcurrentWitness2Test !1198, WitnessLint !1173). Until they are merged, `download-validators.py` finds them only in a copy of fm-tools with those requests applied, given as `--fm-tools-dir`. Two versions of one tool with the same DOI (ULTIMATE Automizer `svcomp27-violation` and `svcomp27-correctness`; WitnessLint's two `2.3-…-witnesses-v2`) are one archive, and the second is a symbolic link to the first.

The components run alone and with `only-<component>` are those the production configurations name (`--components` changes them: a comma-separated list, or `all`). ULTIMATE Automizer and iekke are pool components, not in `conf/svcomp27.json`; their tasks run only with `--components all` or with their names, after `download-tools.py --pool`. A production configuration does not run the tasks only they own (see "What is run").

The exit status is 0 when every check passes, 1 when one fails, 2 when the suite could not run (a missing task, tool or validator, an unreadable configuration, a failed `benchexec` call), with the reason on standard error. The table and the checks go to standard output and to `tests/integration/out/table.txt`; `out/results.json` has every run (status, CPU time, memory, witness, validation) and the failed and passed checks.

Requirements: Linux with BenchExec (`benchexec` on the path, cgroups as BenchExec needs them; tested with BenchExec 3.35), Python 3 with `yaml` (a BenchExec dependency), a `tools/` directory made by `scripts/download-tools.py`, `gcc` with ThreadSanitizer (ConcurrentWitness2Test compiles the program with `-fsanitize=thread`), and the Python packages WitnessLint's fm-tools entry lists (Ubuntu's `python3-lxml`, `python3-jsonschema`, `python3-yaml`, `python3-pycparser`, `python3-clang`; Ubuntu 26.04 without `python3-pycparser` needs `pip install --target DIR pycparser`); a package that is not installed can be put on `PYTHONPATH`, which BenchExec passes on to the runs. Every verifier, validator and `./cooperace` run goes through `benchexec`; nothing is started outside it. The `alone-` runs put the checkout's `lib/benchexec-*.whl` first on `PYTHONPATH`, so the `benchexec` command runs them with the wheel's executor and tool-info modules, the BenchExec version CoOpeRace bundles; the other runs, and the validators, use the installed BenchExec. Set `TMPDIR=/tmp` if `TMPDIR` points to a directory BenchExec overlays (BenchExec's container then refuses to start).

## What is run

Four kinds of verification run, named in the table by their BenchExec run definition:

| Run definition | What it runs |
| --- | --- |
| `alone-<component>` | the component's own tool-info module (`benchexec.tools.goblint`, `.dartagnan`, `.sv-sanitizers`, `.deagle`, `.ultimategemcutter`, and for the pool `.ultimateautomizer`, `.iekke`) with the options `tools-options.json` records for the component, which are the `benchexec_toolinfo_options` of its fm-tools version (for the `svcomp27` versions, Goblint: `--portfolio-conf conf/svcomp27/seq.txt`, ULTIMATE Automizer and GemCutter: `--full-output`, the others: none), started in the component's directory under `tools/`. This is the reference. CoOpeRace adds to these options the options of the component's `WitnessSpec`, which for Goblint include `--set witness.yaml.entry-types ["ghost_instrumentation"]`, so check 3 compares Goblint's verdicts without and with that option. The suite stops with status 2 if `tools/<component>/.doi` is not the DOI that `tools-options.json` records. |
| `only-<component>` | `./cooperace --conf tests/integration/conf/only-<component>.json`: CoOpeRace configured with that component alone, for all four properties, accepting both verdicts. |
| `svcomp27`, ... | `./cooperace --conf conf/<name>.json`: a production configuration of the checkout under test, and any further configuration given with `--config`. A configuration that names a component missing under `tools/` is listed as not run, not as failed. A production configuration runs only the tasks it can answer from an owner: a task none of whose owners has an entry for the task's expected verdict in the configuration's strategy for the task's property is listed below the table as not run, with the reason, since check 5 would fail there by design. With `svcomp27` these are the four tasks owned only by ULTIMATE Automizer or iekke. |
| `goblint-1s` | `./cooperace --conf tests/integration/conf/goblint-1s.json`: a configuration of the suite (`configurations` in `manifest.json`): Goblint, trusted for `true`, with `"cpuTimeLimits": {"Goblint": 1}` in phase 1, then Dartagnan in phase 2 with `"memoryLimits": {"Dartagnan": "70%"}`. It runs a task of its own, `goblint-regression/04-mutex_19-call_by_ptr_rc`, on which level 3 of Goblint's portfolio reaches the limit and Dartagnan then answers `false`. It exercises a CPU-time limit far below the production one, the portfolio runner giving up the remaining levels, a memory limit given as a percentage, and the hand-over to the next phase, in about 8 s of wall time. |

`alone-` and `only-` runs use each component's own tasks only (`owners` in `manifest.json`); `--cross` runs every component on every task. The production configurations run every task, except a task that names `configurations` in `manifest.json`, which only those configurations of the suite run. `./cooperace` is started with the checkout as working directory, since it looks for `tools/` there; the witness it writes is collected from the BenchExec run's result files, and a component alone's from its result files named `*witness.yml` (Deagle writes `error-witness.yml`). BenchExec's tool-info module for CoOpeRace at version 3.35 gives `ERROR` for any verdict line but `true`, `false` and `unknown`; the suite reads a run of CoOpeRace that ends in `CoOpeRace verdict: false(<property>)` as that result, as the module of sosy-lab/benchexec#1337 does.

The witness of every run whose verdict is the task's expected one is collected where a witness can count for it, by CoOpeRace's witness table `conf/witnesses.json`: every `false`, and a `true` of unreach-call or no-overflow. It is validated, as a BenchExec run of the validator the task names in `manifest.json` (a violation validator for a task expected `false`, a correctness validator for one expected `true`), and checked by WitnessLint, as one more BenchExec run per kind of witness (`out/lint/`). The witness is read from the verification run's result files, as the competition reads `results-verified`. The validators are SV-COMP 2027 versions, each with the `benchexec_toolinfo_options` of its fm-tools version; a validator confirms a violation witness by answering `false` and a correctness witness by answering `true`:

| Name in `manifest.json` | Validator | fm-tools version | DOI | Options |
| --- | --- | --- | --- | --- |
| `uautomizer` | ULTIMATE Automizer | `svcomp27-violation` | 10.5281/zenodo.23295622 | `--validate <witness> --full-output --witness-type violation_witness` |
| `theta` | Theta | `svcomp27-validator` | 10.5281/zenodo.23184251 | `--svcomp --portfolio STABLE --loglevel RESULT --witness <witness>` |
| `concurrentwitness2test` | ConcurrentWitness2Test | `svcomp27` | 10.5281/zenodo.21342108 | `--witness <witness>` |
| `uautomizer-correctness` | ULTIMATE Automizer | `svcomp27-correctness` | 10.5281/zenodo.23295622 | `--validate <witness> --full-output --witness-type correctness_witness` |
| `ugemcutter-correctness` | ULTIMATE GemCutter | `svcomp27-correctness` | 10.5281/zenodo.23295738 | `--validate <witness> --full-output --witness-type correctness_witness` |
| (format check of a `false`) | WitnessLint | `2.3-violation-witnesses-v2` | 10.5281/zenodo.23270765 | `--witness <witness> --expectViolationWitness --ignoreSelfLoops --expectedWitnessVersion 2` |
| (format check of a `true`) | WitnessLint | `2.3-correctness-witnesses-v2` | 10.5281/zenodo.23270765 | `--witness <witness> --expectCorrectnessWitness --ignoreSelfLoops --expectedWitnessVersion 2` |

Each task names one validator that confirms the witness of each of the task's owners when the owner runs alone, or none (see "Tasks"). ULTIMATE Automizer and Theta confirm violation witnesses of all four properties; ConcurrentWitness2Test answers `ERROR (ineffective witness)` on those of no-overflow and valid-memsafety and is used for no-data-race only. Not used: CPAchecker's 2027 version (fm-tools !1156, 10.5281/zenodo.23209212), which Zenodo does not serve; Dartagnan's `svcomp27-validation` (!1170), whose wrapper has no `-witness` option and so cannot run as a validator; MetaVal and Witch, whose versions in fm-tools (`svcomp26`) do not support no-data-race; Goblint's and Theta's correctness validators, which do not accept Goblint's `ghost_instrumentation` witness. No witness of a `true` is validated in no-data-race or valid-memsafety, where 2027 neither requires nor scores one.

The witness format is data in `run.py` (`WITNESS_FORMATS`: the file a verifier writes, its validators and its linters with BenchExec tool-info module and options, and how to read the producer from it); `--witness-format` selects the entry. `yaml-2.2`, the default, is SV-COMP 2027's format; `graphml-1.0` is SV-COMP 2026's (`witness.graphml`, the violation validators CPAchecker 4.2.2, Dartagnan `svcomp26-validation` and ULTIMATE Automizer `svcomp26-violation` with the options of their bench-defs definitions `*-validate-violation-witnesses-v1.xml` at tag `svcomp26`, no linter; `download-validators.py --format graphml-1.0` fetches them), and it needs a manifest whose validators are of that format.

## The checks

| # | Check | A failure means |
| --- | --- | --- |
| 1 | No run, in any configuration, gives a verdict different from the task's expected one. | A wrong verdict, in CoOpeRace or in a component alone. |
| 2 | Each component alone gives the expected verdict on its own tasks, and where its witness can count for that verdict and the task names a validator, the validator confirms the witness. | The task is a bad pick (a component or validator behaves differently here than when the task was picked): replace the task. Not a defect of CoOpeRace. |
| 3 | Inside CoOpeRace with `only-<component>`, the component gives the verdict it gives alone (its `Tool name: X Result: V` line), wherever the component alone answered. What CoOpeRace prints can still differ, where the witness table requires a witness the component did not write; check 4 reports that. | The integration changes what the component computes: options, data model, preprocessing, parsing of its output. |
| 4 | Every expected verdict of CoOpeRace for which a witness can count (every `false`; a `true` of unreach-call or no-overflow) delivers a witness file of the format (`witness.yml`) where the witness table `conf/witnesses.json` requires one, that the named validator confirms where the task names one, that the format's linter for its kind (WitnessLint) accepts, and whose producer (`metadata.producer.name`), where it names one, is the component that answered (the `CoOpeRace result from: X` line of CoOpeRace's output). With `only-<component>`, a component that answers the expected verdict inside CoOpeRace makes CoOpeRace print it. | The witness is missing, belongs to another component or run, the validator rejects it, does not have the form the format requires, or does not pass CoOpeRace's own check of its format. |
| 5 | Each production configuration, and each configuration of the suite, gives the expected verdict on every task it runs. | The configuration gives no verdict (`unknown`, timeout, out of memory) or a wrong one on a task that some component answers within the limits. |
| 6 | Every output of CoOpeRace follows its protocol: the last line is `CoOpeRace verdict: true`, `false`, `unknown` or `ERROR (contradiction: ...)` (unless BenchExec ended the run); right before it, for `true` and `false` only, one `CoOpeRace result from: X`; every `---X logs---` is closed by its `---end of X logs---` and followed by `Tool name: X Status: ...`; no line starts with `CoOpeRace: error:`; and a `false` run's result files hold the file of the witness format (`witness.yml`) where the witness table requires a witness for a `false` on the task's property, every file there is `witness.graphml` or `witness.yml` in the format its name says, no two files are in one format (a component may write both, as ULTIMATE Automizer `svcomp27` does), and, for the YAML format, each YAML file has exactly one `violation_sequence` entry, whose `format_version` is one that the witness table accepts for a `false` on the task's property (its `minimumVersion` to its `highestVersion`, 2.2 to 2.3); a `true` run's result files hold `witness.yml` where the witness table requires a witness for a `true` on the task's property (unreach-call, no-overflow), and its `invariant_set` and `ghost_instrumentation` entries have one `format_version` that the table accepts for it (2.1 to 2.3). | CoOpeRace's output or witness delivery changed in a way that `benchexec.tools.cooperace` (which reads only the last line), this suite or a validator depends on, or CoOpeRace ended with an error of its own, which it reports as a line `CoOpeRace: error: ...` and no verdict line. |
| 7 | Wherever a configuration gives a component a limit (`memoryLimits`, `cpuTimeLimits`), CoOpeRace's output has `Memory limit of X: N bytes` or `CPU-time limit of X: N s` whenever X started, with N the configured value; for a percentage, within 1 % of that percentage of the memory limit BenchExec records for the run (`memlimit` in the result XML). Wherever a phase has a `wallTimeLimit`, a line `CoOpeRace: the wall-time limit of phase N, L s, has passed: ...` gives that limit, and a component that is in that phase only (in neither the phase before nor the one after) ended within L and 5 s, by the `walltime` of its `Tool name: X Measured:` line. | CoOpeRace did not set the limit it was configured with, or set another one: for a percentage, `run_memory_limit` did not find the run's cgroup limit inside BenchExec's container on this machine, and the component ran without a limit of its own; or a phase's wall-time limit did not stop its components. |
| 8 | On every hand-over task (`"hand_over": true` in `manifest.json`), in every configuration that runs it: no component of phase 1 has a `CoOpeRace answer:` line; a component that is in phase 1 only ends without a verdict, and at least one of them reaches a limit, either status `TIMEOUT` with a `cpuTimeLimits` entry whose value its `Measured:` line shows used (at least 90 %), or stopped at phase 1's `wallTimeLimit`; and the verdict comes from a component that is in phase 2 only (`CoOpeRace result from: X`) and is the expected one. | A limit of phase 1 did not end its component (the limit was not applied, or the component answered or gave up early on this machine: then the task is a bad pick), or CoOpeRace did not start phase 2 or took the verdict from phase 1. |
| 9 | In every output of CoOpeRace, no component's block appears twice, and in particular a component listed in two consecutive phases is started once; the verdict line is the one that the `CoOpeRace answer: X V, bracket N, ...` lines decide by the rules of [`conf/README.md`](../../conf/README.md) (the highest bracket with an answer decides, `true` beside `false` there is a contradiction, and a `false` needs a witness, taken from the first of `witnesses`, else of the deciding bracket by name), with `CoOpeRace result from: X` naming the component it is taken from; and no component that could still have changed the verdict was stopped, unless a phase's wall-time limit stopped it: none with an entry above the deciding bracket, and none with an entry for the other verdict in it. The report lists, below check 9, each run in which a component of two consecutive phases ran once while the later phase started another component. | CoOpeRace printed a verdict its components' answers do not give, stopped a component whose answer could have changed it, or ran a component twice. |

Check 1 also covers what 5 says about wrong verdicts, so a wrong verdict of a production configuration fails both. Checks 6 to 9 read CoOpeRace's output in the BenchExec log of each run; `src/cooperace/` prints it (`print_component_run` and `announce_limits` in `components.py`, `run_strategy` and `execute` in `strategy.py`) and the launcher `cooperace` prints the verdict line. A task that only one component answers makes a production configuration depend on that component's integration: that is the point of choosing such tasks, since another component's answer cannot hide a broken integration.

## Limits

The suite's own limits, far below the competition's (4 cores, 15 GB, 900 s CPU time for a verification run, 2 cores, 7 GB, 90 s for a validation run), so that it is fast and many runs fit beside each other:

- verification run: 2 cores, 1 GB memory, 90 s CPU time (hard limit 112 s), 120 s wall time;
- validation and linter run: 2 cores, 1 GB memory, 90 s CPU time (hard limit 120 s), 120 s wall time.

`--cores`, `--memlimit` (both kinds of run), `--timelimit`, `--walltimelimit`, `-j`, `-N` and `--allowed-cores` change them. The longest runs are the hand-over tasks of unreach-call and no-overflow in `svcomp27`, up to 51 s of CPU time and 46 s of wall time: Goblint's 30 s of CPU time in phase 1, then ULTIMATE GemCutter in phase 2. The time limits leave room for a phase 1 that ends at its wall-time limit of 45 s instead, which no task of the suite exercises. The no-data-race and valid-memsafety tasks on which sv-sanitizers finds nothing take 34 s in `svcomp27`, its 30 s of CPU time. Every run stays below 900 MB; the largest are `svcomp27` (860 MB, Goblint, Dartagnan and GemCutter at once) and `only-ugemcutter` (650 MB). The report gives the peak memory (BenchExec's `memory` column) of each run definition, validator and linter, and the wall time of each stage.

## Tasks

`manifest.json` lists each task with its property (`property`, no-data-race where it names none), its owners (the components that are expected to answer it alone), whether it is a hand-over task (`hand_over`), the configurations of the suite that alone run it (`configurations`, where it has one), the validator, its origin, its licence and what SV-COMP 2026 recorded for each component (`sv_comp_2026`: verdict and CPU time of the component's own run, or the status). Tasks are copies from `sv-benchmarks` at tag `svcomp26` (commit 7efe28dd29576b46927b7a34e8f742bd90966a75) with the `.yml` reduced to the task's property; a task of the same name there carries the original `.yml`. All are ILP32, except the two LP64 programs written for the suite. Their source is the `.c` beside each `.i`; the `.i` is `cpp -P race-only-on-lp64.c > race-only-on-lp64.i` (and the same for `race-only-on-ilp32`) on x86-64 (GCC 15.2, glibc 2.43 of Ubuntu 26.04), which leaves out line markers: Dartagnan `svcomp27` ends in `ERROR` on a `.i` whose line markers name the `.c`, since it cannot place the witness's waypoints in the file it was given. Licences are those of the task's directory in `sv-benchmarks`, texts in `LICENSES/` at the root of the repository (REUSE.toml lists the license of each file without a header).

Tasks were picked from the verified SV-COMP 2026 results of the four sub-categories of `C.Concurrency` (for no-data-race, also the validated ones): the owner answers alone within 10 s CPU time (GemCutter within 25 s), and no other component of the property's strategy in `conf/svcomp27.json` gives an answer that the strategy accepts from it. A component may answer a verdict for which the strategy has no entry for it (GemCutter's `false`, Deagle's `true` in unreach-call and no-overflow); CoOpeRace ignores such an answer, so it cannot hide the owner. Each pick was then run with the components' `svcomp27` versions, which differ from 2026: `goblint-regression/06-symbeq_14-list_entry_rc`, where Goblint answered no-overflow `true` in 0.1 s in 2026, is `unknown` with Goblint `svcomp27`. A hand-over task is one on which a phase-1 component reaches a limit without answering and a phase-2 component of the property answers, and on which no component that CoOpeRace keeps running in phase 2 runs to the suite's limits.

`goblint-regression/04-mutex_19-call_by_ptr_rc` (no-data-race, expected `false`) is the hand-over task of `goblint-1s`: Goblint `TIMEOUT` at its 1 s, then Dartagnan answers `false` and ULTIMATE Automizer's validator confirms its witness. Goblint's own run needs 54 s to end in `unknown` there, too long for the other configurations.

The tasks of the pool components, run only when `--components` names them: ULTIMATE Automizer `true` on `ldv-races/race-4_1-thread_local_vars` (the only task of the category on which it alone answers `true`, 42 s CPU in SV-COMP 2026) and `pthread-theta/unwind2-nondet`, ULTIMATE Automizer `false` on `goblint-regression/04-mutex_50-funptr_rc` (Theta confirms) and `04-mutex_21-sound_base` (ConcurrentWitness2Test confirms), and both LP64 programs; iekke `true` on `pthread/queue` (no-overflow).

Why each task, in more detail, is its `purpose` in `manifest.json`. Points to keep in mind:

- `lp64/race-only-on-lp64` has a data race only when `sizeof(long) == 8`, so it is expected `false` under LP64, and `race-only-on-ilp32` is the same program with the indices swapped, expected `true`. A component given ILP32 reports the opposite; ULTIMATE Automizer does. In `svcomp27`, sv-sanitizers answers `false` on the first and finds nothing on the second, so CoOpeRace passes the data model to it. Dartagnan's tool-info module passes no data model, so for Dartagnan the tasks check only that its verdicts are the LP64 ones.
- A configuration that starts with Goblint spends Goblint's time on every task before a phase-2 component starts, so a task on which Goblint needs long to end in `unknown` (169 s CPU time on `pthread-divine/ring_1w1r-2`) does not fit the suite's limits. Outside the hand-over tasks, the tasks were chosen with Goblint ending in `unknown` within 2 s (8 s on `libvsync/clhlock`).
- `libvsync/clhlock` names no validator. sv-sanitizers' witness there has one target waypoint and format version 2.0, which does not pass CoOpeRace's check, so CoOpeRace prints the `false` without a witness; a valid-memsafety `false` needs none (demo mode in 2027). No 2027 validator confirms the witness within the suite's limits: ULTIMATE Automizer `svcomp27-violation` runs out of memory at 4 GB and at 7 GB, and so at the suite's 1 GB, and Theta reaches 90 s. The two other valid-memsafety tasks on which sv-sanitizers alone answers `false` in 2026 (`goblint-regression/28-race_reach_86-lists_racing-deref`, `-87-lists_racefree-deref`) fare no better: Automizer runs out of memory and Theta ends in `ERROR (frontend failed, after parsing finished)`.

## Output directory

`out/` (git-ignored) holds `meta.json` (machine, BenchExec version, commit of the checkout and its `git describe --always --dirty`, `tools.txt`, limits, and the run definitions with their tasks), `defs/` (the generated BenchExec definitions), `verify/` and `validate/` (BenchExec's results, logs and result files), `witnesses/<run definition>/<task>.yml/witness.yml` (the witnesses that were validated), `lint/` (WitnessLint's runs), `table.txt` and `results.json`. BenchExec writes the environment of the process that starts it into every result XML. `run.py` therefore starts BenchExec without any environment variable whose name contains `TOKEN`, `SECRET`, `PASSWORD` or `KEY`, in any case (and with `TMPDIR=/tmp`); other variables are still recorded, so look through a result XML before sharing it.

`run.py validate --out DIR` validates and checks the verification runs already in DIR; `run.py check --out DIR` only rebuilds the table and the checks, which is how a change to a check is tried without rerunning anything. Both take the run definitions and tasks from `DIR/meta.json`, not from the options that choose them, and ignore results in DIR of run definitions or tasks that `meta.json` does not list.

## Known limits of the suite

- Witnesses differ from run to run (ULTIMATE Automizer's, Dartagnan's, sv-sanitizers' carry a creation time and are recomputed), and ConcurrentWitness2Test executes the program repeatedly. A task whose validator confirms one run's witness and times out on another's is a bad pick; the tasks were chosen so that the validators confirm the witnesses of the runs made when the validators were picked.
- Goblint alone, without `--set witness.yaml.entry-types ["ghost_instrumentation"]`, writes a correctness witness whose entries carry format versions 2.1 and 2.0, which WitnessLint rejects (`lint ERROR (invalid witness syntax)` in its cells); CoOpeRace runs Goblint with the option, and its witness passes. Check 2 does not read the linter, so this is shown, not failed.
- With `--components all`, two known component defects fail checks: iekke 2.0 (10.5281/zenodo.23243599) gives no answer on any task, since its wrapper `iekke` opens `output_unwind_rounds.csv` in its directory, which the archive does not contain (check 2 fails on `pthread/queue`); and ULTIMATE Automizer `svcomp27`'s no-data-race witnesses end with one `target` waypoint, which WitnessLint rejects (check 4 fails on the `only-uautomizer` runs of its `false` tasks).
- The data model is tested by two LP64 programs; no task of the SV-COMP `C.Concurrency` categories in the suite is LP64.
